# TradeBot 사업모델 회의록

**일시:** 2026년 6월 11일  
**참석자:** 개발자/오너 (SAP 컨설턴트, 10년+ 주식 매매 노하우)  
**주제:** TradeBot 제품화 및 판매 전략 전반

---

## 1. 배경 및 출발점

- TradeBot은 "뒷차기2" 엔진 기반의 레인보우 차트 + Claude AI 통합 자동매매 시스템
- 현재 개인 온프레미스 Windows PC에서 운영 중 (포트 5000, 운영서버)
- 키움증권 REST API 연동, 에이전트 없이 직접 호출 구조로 이미 전환됨
- 제품화 방향 검토 필요 시점 도달

---

## 2. 제품화 방식 검토

### 2-1. 소스코드 직접 판매 (GitHub)
- 구매자가 직접 설치/운영
- 투자 책임 완전히 구매자에게 귀속
- 장점: 법적 리스크 최소, 구현 부담 없음
- 단점: 1회성 수익, 설치 난이도 높음, 복제/유출 통제 어려움

### 2-2. SaaS 구독 모델
- 클라우드 서버에서 다수 사용자가 접속
- 논의 결론: **키움 REST API가 공인IP 기반 토큰 인증 방식**이므로 SaaS 구현 기술적으로 가능
- 사용자는 키움 개발자 포털에서 SaaS 서버의 고정 공인IP를 허용 IP로 등록
- 사용자 APP KEY/SECRET은 DB에 암호화 저장 → 서버가 대신 API 호출
- **현재 코드 구조가 이미 멀티테넌트:** `userId` 기반 격리, 모델/계좌/거래 전부 분리됨
- 추가 개발 필요 사항: 결제 연동(Paddle), 플랜 관리, 온보딩 가이드

### 2-3. 인프라 결정
- **결제: Paddle** 채택
  - Merchant of Record 방식 → 세금/VAT/환불 Paddle이 대신 처리
  - USD 기본 청구 (KRW도 지원) → 글로벌 판매 가능, 환율 이익
  - 구독 관리 내장, 개발자는 API 연동만
  - 수수료 5% + $0.50 → 고가 SaaS 구조에서 충분히 감당 가능
- **Railway** 채택: Node.js 서버 + PostgreSQL + 고정 Outbound IP 제공
  - AWS는 초기 단계 오버킬, 유저 수 증가 후 이전 검토
  - Supabase는 DB 전용, 트레이딩 엔진 워커 실행 불가 → Railway 단독 사용 결정

## 3. 3티어 판매 모델 확정

### 티어 1: Public SaaS (공유 구독)
- 공용 서버에서 다수 사용자 운영
- 설정값(파라미터)만 조정 가능, 코어 수정 불가
- 업데이트 자동 반영

**과금 구조 (투자금 + 계좌 기준, 모의계좌 제외):**

| 구간 | 월 구독료 |
|------|----------|
| 계좌 1개 + 투자금 ~2,000만원 | 12만원 |
| 계좌 1개 + 투자금 ~5,000만원 | 25만원 |
| 계좌 1개 + 투자금 ~1억원 | 45만원 |
| 1억 초과 또는 다계좌 | 협의 |

- 투자금 자동 검증 가능: 사용자 API 키로 계좌 잔고 조회 → 티어 자동 판정
- 차별화 포인트: 일반 퀀트 도구와 비교 불가한 10년 노하우 + 실전 검증 시스템

---

### 티어 2: Private Cloud (프라이빗 클라우드)
- **SAP Private Cloud 모델 동일 구조** 채택
- 전용 독립 인스턴스 (Railway 별도 프로젝트)
- 거래 데이터 완전 격리 — **공용 AI 학습에 절대 미사용** (핵심 셀링 포인트)
- **Extension Layer 커스터마이징 허용** (코어 수정 불가, SAP BAdI 방식)

**Extension Layer (수정 허용 범위):**
- AI 프롬프트 템플릿
- 스캔 조건 로직 (커스텀 전략 추가)
- 리포팅 대시보드 레이아웃
- 매도 전략 커스텀 룰

**Core Engine (수정 불가):**
- 주문 실행 로직
- 키움 API 연동
- DB 스키마 코어

**계약 구조 (SAP 구현 프로젝트 방식):**
- 초기 구현비 (1회성): 500만~1,000만원
  - 전용 인스턴스 셋업 + Extension 커스터마이징 + 교육 포함
- 연간 유지 구독: 월 50만~100만원
  - 코어 업데이트 반영 + 기술지원 포함

---

### 티어 3: Private Installation (완전 프라이빗 설치)
- 소스코드 전체 포함, 고객 서버에 직접 설치
- Core 포함 전체 수정 가능, 소유권 이전
- 가격: **3,000만원 ~ 5,000만원**
- 계약 필수 조건:
  - 소스코드 재판매/공유 절대 금지
  - 1인/1법인 사용 제한
  - 유지보수 별도 계약 (판매가의 15~20%/년)
  - 업데이트 별도 계약

## 4. 법적/규제 리스크 대응

- 한국 자본시장법상 **투자자문업 등록 필요 조건**: 투자 판단을 대신 제공하는 경우
- **TradeBot 포지셔닝**: "사용자가 직접 설정한 전략을 실행하는 자동화 도구"
  - TradingView의 지표 판매와 동일한 법적 성격
- **모든 판매 계약서/약관 필수 포함 사항:**
  1. 이 소프트웨어는 자동화 도구이며 투자자문이 아님
  2. 투자 손실에 대한 책임은 전적으로 사용자에게 있음
  3. 시스템 장애로 인한 미체결/오체결 책임 한계
  4. 구독 해지 시 데이터 처리 방침
  5. 소스코드 재판매/공유 금지 (티어 3)

---

## 5. 세일즈 전략

- **Public SaaS**: 온라인 마케팅, 실적 데이터(수익률/승률/MDD) 공개로 신뢰 구축
- **Private Cloud / Private Install**: 소개/신뢰 기반 영업 (고액 개인 투자자, 소형 투자조합)
  - 순서: SaaS로 실적 데이터 축적 → 그 데이터로 프라이빗 영업
- 과금 정당화 근거: 모의투자 6개월+ 수익률, 승률, MDD 공개 필수

## 6. 개발 우선순위 (다음 단계)

### ⚠️ 운영 보호 원칙 (추가 결정)

> **현재 로컬 Windows PC(포트 5000)에서 실계좌 자동매매가 운영 중.**
> Railway CI/CD는 Staging 환경에만 연결하고, 로컬 운영은 Railway Production 전환 결정 전까지 절대 건드리지 않는다.
> - `dev` 브랜치 push → Railway Staging 자동 배포
> - `main` 브랜치 → 로컬 `deploy.bat` 방식 유지 (변경 없음)
> - Railway Production 연결 시점 → Phase 1 완료 후 별도 협의

---

### Phase 1 — SaaS 런칭 준비 (핵심)
1. Railway 배포 환경 구성 + 고정 IP 설정
2. Paddle 구독 결제 연동
3. 플랜/티어 관리 (가입 → 플랜 선택 → 결제 → 활성화)
4. 사용자별 AI 사용량 한도 + 자동 티어 판정 (잔고 조회 기반)
5. 온보딩 가이드 ("키움 앱키 발급 후 이 IP 등록" 단계별 안내)
6. 약관/계약서 작성 (법무 검토 권장)

### Phase 2 — Private Cloud 준비
7. Extension Layer 경계 설계 (코어 vs 확장 분리)
8. 전용 인스턴스 빠른 배포 스크립트 (신규 고객당 Railway 프로젝트 자동 생성)
9. 월간 성과 리포트 PDF 출력

### Phase 3 — Private Install 패키징
10. 설치 가이드 문서화
11. 라이선스 키 검증 시스템
12. 소스코드 난독화 검토 (코어 부분)

## 8. 코드베이스 아키텍처 결정 — 단일 레포 전략

### 논의 배경
- 온프레미스 / 프라이빗 클라우드 / 퍼블릭 클라우드 환경을 아우르려면 코드를 분리해야 하는가?
- 분리 시 기능 개발 동기화 문제 (아직 완성품이 아니므로 계속 기능 추가 중)
- 하나의 레포에 전부 넣으면 온프레미스 코드가 SaaS에 노출되지 않는가?

### 결정: **단일 코드베이스, 환경변수로 티어 제어**

```
DEPLOYMENT_TIER=public_saas    → Railway 공용 서버
DEPLOYMENT_TIER=private_cloud  → Railway 전용 서버 (고객별 인스턴스)
DEPLOYMENT_TIER=on_prem        → 고객 서버 직접 설치
```

### 근거
- SAP S/4HANA, GitLab CE/EE 동일 구조 — 같은 코드베이스, 라이선스/설정이 기능을 제어
- **"환경 차이"이지 "코드 차이"가 아님**
- 코드 분리 시 버그 수정 하나에 3개 레포 반영 필요 → 기능 동기화 악몽

### 소스코드 노출 우려 해소
| 티어 | 소스 노출 여부 | 이유 |
|------|--------------|------|
| Public SaaS 사용자 | 없음 | 브라우저에서 서버 코드 접근 불가 |
| Private Cloud 고객 | 없음 | Railway 서버 접근 권한 없음 |
| Private Install 고객 | 있음 (의도적) | 3~5천만원에 소스코드 포함 판매 |

- 플랜별 사용량 한도 체크
