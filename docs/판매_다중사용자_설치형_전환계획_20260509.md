# 판매/다중사용자 전환 계획서 (개인용 -> 서비스형/설치형)

작성일: 2026-05-09
대상: 현재 개인용 tradebot

## 목적
- 개인용 봇을 "다른 사람도 안전하게 쓸 수 있는 제품"으로 전환
- 웹형(SaaS)과 설치형(자기 PC 실행) 둘 다 지원 가능한 구조 확보
- 기능보다 먼저 보안/권한/키관리/운영 안정성을 표준화

---

## 1) 사용자별 API 키/계좌 분리

### 목표
- 각 사용자가 본인 API 키와 계좌만 등록/사용
- 운영자 포함 타 사용자 계좌 접근 불가

### 변경 포인트
1. 사용자별 시크릿 저장소 분리
- `user_id` 단위로 키 저장
- 평문 금지(암호화 저장)

2. 계좌 소유권 강제
- `accounts.user_id`와 현재 로그인 `user_id` 반드시 일치할 때만 접근 허용
- 모든 주문/조회 API에서 서버 측 재검증

3. 키 입력 UX
- 설정 화면에서 사용자 본인 키 입력/갱신
- 마지막 갱신 시각, 연결 성공/실패 상태 표시

---

## 2) 로그인/계정 보안 강화

### 최소 필수
1. 비밀번호 해시 강화(이미 해시 사용 중이면 정책 강화)
2. MFA(OTP) 옵션 제공
3. 세션 보안 옵션 강화(만료, 재로그인, 동시세션 제한)
4. 주요 이벤트 감사 로그
- 로그인 실패 반복
- 키 변경
- 주문 실행/중지

### 권한 정책
- "내 계정 -> 내 데이터만"을 라우트 단위로 강제
- 관리자 권한은 별도 역할(Role) 분리

---

## 3) 승인된 사용자만 접근(초대/화이트리스트)

### 운영 방식
1. 공개 회원가입 OFF
2. 초대코드 또는 운영자 승인 기반 가입
3. 상태값 관리
- `pending`(승인대기)
- `active`(사용가능)
- `suspended`(중지)

### 필요한 화면/API
- 운영자: 사용자 승인/거절/중지 관리 화면
- 사용자: 가입 후 승인 대기 상태 안내 화면

---

## 4) 타 사용자 거래데이터 공동학습(개인정보 제외)

### 방향
- "옵트인(동의한 사용자만)" 기반
- 원본 거래기록 직접 공유보다 "익명화/집계 피처" 공유 권장

### 필수 원칙
1. 개인식별 제거
- 계좌번호, 사용자 식별자, 메모 원문 등 제거

2. 재식별 방지
- 시점/수량/종목 조합으로 개인이 특정되지 않도록 범주화/버킷화

3. 철회권
- 사용자가 공동학습 동의를 철회하면 이후 데이터 수집 중단

4. 로그 분리
- 개인 리포트용 데이터와 공동학습 데이터 파이프라인 분리

---

## 5) 자기 PC 설치형(가장 중요한 질문)

## 핵심 결론
"가능"합니다. 그리고 오히려 자동매매 특성상 설치형이 현실적으로 유리한 면이 큽니다.

## 설치형을 쉽게 설명하면
- 지금: 웹서버 + 에이전트 + DB를 개발자처럼 직접 실행
- 설치형 목표: 사용자는 `설치 파일 실행 -> 다음 -> 완료`만 하면 자동으로 실행

즉, 사용자가 서버 명령어를 몰라도 됩니다.

## 동작 구조(설치형)
1. 로컬 서비스(백엔드) 실행
- Windows 서비스 또는 백그라운드 프로세스로 상시 실행

2. 로컬 에이전트 실행
- 키움 API/HTS 연동 담당

3. UI 앱 실행
- 브라우저 또는 데스크톱 앱(Electron/Tauri)
- 내부적으로 `http://localhost:포트`에 접속

4. 로컬 DB 사용
- 초기에는 SQLite 가능
- 고급 사용자는 PostgreSQL 선택 설치 가능

## 사용자가 보는 경험
1. 설치 프로그램 실행
2. 최초 실행 마법사
- 계정 생성/로그인
- API 키 입력
- 모의/실전 계좌 연결
3. "시작" 누르면 자동매매 준비 완료

## 설치형에서 꼭 챙길 점
1. 자동 업데이트
- 앱/에이전트/룰셋 버전 동기화

2. 장애 복구
- 재부팅 후 자동 시작
- 로그 수집/복구 버튼

3. 보안
- 로컬에 저장된 비밀키 암호화
- 외부 접근 차단(기본 localhost only)

4. 운영지원
- 원격진단 로그 내보내기(사용자 동의 시)

## 설치형 구현 단계(권장)
1. 1단계: 현재 구조를 "원클릭 실행" 스크립트로 단순화
2. 2단계: Windows 서비스 등록 + 트레이 앱
3. 3단계: 정식 설치파일(MSI/EXE) + 자동업데이트

## 부록 D) 설치형(자기 PC) 이해를 위한 1페이지 요약

### D-1. 사용자는 이렇게 보게 됨
1. 설치파일 실행
2. "다음" 몇 번 클릭
3. 바탕화면 아이콘 실행
4. 자동으로 로컬 서비스/에이전트가 뜨고 화면이 열림

### D-2. 내부에서는 이렇게 동작
- 로컬 서버: `localhost`에서 API/UI 제공
- 로컬 에이전트: 키움 연동/주문 담당
- 로컬 DB: 사용자 PC에 저장
- 필요 시 중앙 서버: 인증/라이선스/업데이트 확인

### D-3. 왜 이 구조가 좋은가
- 사용자는 명령어 몰라도 됨
- 브로커 연동은 사용자 PC에서 직접 처리 가능
- 장애 시 로그 수집/복구가 쉬움

### D-4. 1차/2차 로드맵
- 1차: 원클릭 실행 + 자동 점검 + 로그 내보내기
- 2차: 정식 설치파일(MSI/EXE) + 자동 업데이트 + 서비스 등록

## 부록 F) 보안 기능 구현 계획 (해킹/오남용 대응 중심)

### F-1. 목표
- 자동매매 핵심 기능을 유지하면서 계정 탈취, 키 유출, 무단 주문, 에이전트 위장 접속을 방지
- 보안을 "설정값"이 아니라 "사용자 기능"으로 제공
- 사고 시 즉시 중지/복구/추적 가능한 운영 체계 확보

### F-2. 위협 시나리오(우선 대응)
1. 비밀번호 탈취 후 무단 로그인
2. API 키 노출로 계좌 오남용
3. 허가되지 않은 PC/에이전트가 주문 시도
4. 비정상 주문 폭주(금액/횟수 과다)
5. 설정 변경 후 책임 추적 불가

### F-3. 우선순위 로드맵

#### P0 (즉시 적용)
1. 로그인 보안 강화
- 로그인 실패 횟수 제한 + 잠금(쿨다운)
- 세션 만료(유휴/절대) 및 전체 세션 로그아웃
- 새 기기 로그인 알림(최근 로그인 이력 제공)

2. API 키 금고
- API 키 암호화 저장(평문 금지)
- 키 마지막 사용 시각/최근 실패 횟수 표시
- 키 즉시 폐기(Disable) 버튼

3. 주문 안전장치
- 1회 최대 주문금액 제한
- 1일 최대 주문금액/횟수 제한
- 비정상 연속 주문 감지 시 자동 정지(킬스위치)

4. 에이전트 신뢰 검증
- 등록된 디바이스만 주문 허용(디바이스 바인딩)
- 에이전트 토큰 주기적 갱신/강제 폐기
- 중앙↔에이전트 요청 서명 검증(재전송 방지 nonce 포함)

5. 감사로그 강제
- 로그인, 키 변경, 주문 실행/중지, 주요 설정 변경 로그 저장
- 관리자/사용자용 로그 조회 화면 분리

#### P1 (다음 단계)
1. MFA(OTP) 선택형 도입
2. IP 허용 목록(관리자/고가 사용자 옵션)
3. 이상행위 탐지 룰(평소 패턴 대비 이탈 탐지)
4. 사고 대응 모드(자동 "모의모드 전환" 또는 주문 중지)
5. 감사로그 내보내기(PDF/CSV) 및 무결성 해시

### F-4. 화면 기능 추가 범위
1. 설정 > 보안센터
- MFA ON/OFF
- 로그인 이력/활성 세션/전체 로그아웃
- 디바이스 목록(허용/차단)

2. 자동매매 > 주문 안전장치
- 1회/1일 주문 한도
- 연속 주문 정지 임계값
- 수동 킬스위치(즉시 주문 중지)

3. 설정 > API 키 관리
- 키 상태(정상/실패/만료)
- 최근 사용 시각
- 키 폐기/재등록

4. 관리자 > 감사로그
- 사용자별 보안 이벤트 조회
- 위험 이벤트 필터(로그인 실패 폭주/주문 폭주/키 변경)

### F-5. 서버/엔진 반영 원칙
1. "화면 저장"만으로 끝나지 않도록, 주문 직전 서버 재검증 강제
2. 사용자 권한 검증 실패 시 주문 차단 + 감사로그 기록
3. 에이전트 인증 실패 시 즉시 연결 해제 + 재인증 요구
4. 위험 이벤트는 알림 발송(앱 배너 + 운영자 채널)
