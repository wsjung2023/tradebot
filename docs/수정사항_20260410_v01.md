## 1. 문제가 뭐야? (초등학생도 알게 설명)

### 비유: 편의점 알바생과 본사

```
집 PC 에이전트 = 편의점 알바생
Replit 서버   = 편의점 본사
PostgreSQL DB = 본사 창고 (할 일 목록이 들어있음)
```

지금 알바생이 **3~4초마다** 본사에 전화해서 "할 일 있어요?" 라고 물어봅니다.
본사는 창고 뒤져보고 "없어요" 하고 끊습니다.
이걸 **하루 28,800번** 반복합니다.

대부분의 통화는 "없어요"입니다. 순수 낭비입니다.

### 실제 비용

| 항목 | 수치 |
|---|---|
| 요청 횟수 | ~20회/분 = 28,800회/일 = **1,050만 회/년** |
| DB 쿼리 수 | 요청 1번당 쿼리 2개 = **2,100만 쿼리/년** |
| Autoscale 비용 | $7.42 청구됨 (KiwoomStockAI 2,736,366 compute units) |
| PostgreSQL 비용 | $4.87 청구됨 (KiwoomStockAI 50.81 hours) |

## 2. 왜 지금 방식이 나쁜가?

### 지금 방식 (Short Polling)

```
에이전트: "할 일 있어요?" → 서버: DB 확인 → "없어요" (연결 끊김)
---3초 후---
에이전트: "할 일 있어요?" → 서버: DB 확인 → "없어요" (연결 끊김)
---3초 후---
(장중이든 장외든 주말이든 24시간 365일 이걸 반복)
```

### 개선 방식 (Long Polling)

```
에이전트: "할 일 있어요?"
서버: 잠깐 기다려봐... (연결을 끊지 않고 30초 동안 내부적으로 체크)
  └── 2초마다 DB 확인
  ├── 할 일 생기면? → 즉시 "이거 해줘!" 응답
  └── 30초 동안 없으면? → "없어요" 응답 후 재연결

---30초 후---
에이전트: "할 일 있어요?" (다시 반복)
```

## 3. 장중 폴링 타임아웃: 왜 30초인가?

### 핵심 질문: "30초 늦게 주문 처리돼도 괜찮나?"

이 앱의 자동매매는 **1분봉 기반 레인보우 차트**를 씁니다.

```
1분봉 = 60초짜리 캔들 하나
레인보우 라인 = 수십 개 캔들의 평균값
```

레인보우 라인 값이 30초 사이에 드라마틱하게 바뀌지 않습니다.
즉, "지금 파란색 라인 아래야 → 사야 해" 신호가 나왔을 때
30초 안에 처리하면 가격 슬리피지(가격 차이)가 무시할 수준입니다.

### 기술적 최대 한계

```
Replit autoscale 환경의 nginx 연결 타임아웃 ≈ 75~90초
안전 마진 적용: 75초 × 0.6 = 45초
추가 여유분: 30초 선택 (안전하게)
```

30초면 매매 품질에 영향 없고, 서버 연결도 안전합니다.

### 비교 표

| 타임아웃 | 요청수/분 | 매매 품질 | 비용 |
|---|---|---|---|
| 현재 (3~4초) | 20회 | 기준 | 기준 |
| 5초 | 12회 | 동일 | 40% 감소 |
| 15초 | 4회 | 동일 | 80% 감소 |
| **30초 (선택)** | **2회** | **동일** | **90% 감소** |
| 60초 | 1회 | 동일 | 95% 감소 |

**30초 선택 이유**: 비용 90% 감소하면서 nginx 타임아웃(75초) 이내로 안전

## 4. 장외(15:30~09:00)와 주말은 어떻게?

### 장외에 에이전트가 해야 할 일

- 자동매매: 없음 (장 닫힘)
- 스케줄 잡: 없음 (워커가 장외엔 잡 생성 안 함)
- 사용자 수동 버튼: 잔고조회, 종목조회 → 버튼 클릭시에만 잡 생성

### 기존 계획(60초 폴링) vs 실제 최선

| 방식 | 비용 | 문제점 |
|---|---|---|
| 60초 Long Poll | 1회/분 | 에이전트 온라인 상태 확인 안됨 |
| 완전 중단 | 0 | 수동 버튼 누르면 에이전트 응답 못함 |
| **heartbeat 분리** | 최소 | 깔끔하게 분리 가능 |

**채택 방법**: `jobs/next`에서 에이전트 상태 확인 역할을 분리하고,
별도의 heartbeat API(`/api/kiwoom-agent/heartbeat`)를 만듦.
- heartbeat: 에이전트가 60초마다 호출 (DB 쿼리 없음, 메모리만)
- jobs/next: 잡이 생길 때만 에이전트가 명시적으로 요청

단, 에이전트 PC 코드 수정이 필요하므로 **1단계에서는 장외 30초 Long Poll 유지**하고
heartbeat 분리는 별도 작업으로 추후 진행.

## 6. DB 쿼리 최적화: 만료 잡 정리

### 현재 문제

`getNextPendingJob()` 함수 안에 만료 잡 정리 코드가 들어있음.
잡 조회할 때마다 만료 정리도 같이 실행됨 = **1회 호출당 쿼리 2개**.

```
쿼리1: 30초 이상된 pending 잡 찾아서 error로 바꿔라 (만료 정리)
쿼리2: 현재 pending 잡 중 가장 오래된 거 1개 찾아서 processing으로 바꿔라
```

### 개선

만료 정리 쿼리를 `getNextPendingJob()`에서 꺼내서 **5분마다 별도 실행**.

```
getNextPendingJob() → 쿼리 1개만 실행 (잡 조회)
5분마다 별도 타이머 → 만료 잡 정리 쿼리 1개 실행
```

그리고 만료 시간을 30초 → **120초**로 늘립니다.
이유: Long Polling으로 최대 30초 기다렸다가 재연결하므로
      30초 만료면 타이밍에 따라 잡이 사라질 수 있음.

## 7. KIWOOM_APP_KEY_MOCK 오류 수정

### 문제

모의계좌 선택 시 `KIWOOM_APP_KEY_MOCK` 환경변수를 찾는데
실제로 등록된 환경변수는 `KIWOOM_APP_KEY`와 `KIWOOM_APP_SECRET`만 있음.

```
실제 환경변수:
  KIWOOM_APP_KEY    ← 모의계좌용
  KIWOOM_APP_SECRET ← 모의계좌용
  KIWOOM_KEY_59190647    ← 실계좌 (계좌번호별)
  KIWOOM_SECRET_59190647 ← 실계좌 (계좌번호별)

코드가 찾는 것:
  KIWOOM_APP_KEY_MOCK    ← 존재하지 않음! → 실패
```

### 수정

`_MOCK` 참조를 전부 제거하고 `KIWOOM_APP_KEY` 직접 사용.
