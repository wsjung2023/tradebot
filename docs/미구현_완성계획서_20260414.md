## 2. 구현 완료 현황 ✅

이 항목들은 코드 및 실행 확인 완료.

```
핵심 자동매매 파이프라인
  ├─ scanJob (30분): 뒷차기2 조건검색 → DART 필터 → candidate_stocks 저장 ✅
  ├─ tradingJob (1분): evaluateCandidateStock → GPT분석 → 레인보우 → 매수/추가매수 ✅
  ├─ learningJob (16:00): optimizeModel() → winRate 분석 → minAiConfidence 자동조정 ✅
  ├─ comprehensiveAiAnalysis(): GPT 2개 병렬 + 거래량 점수 → confidence ✅
  └─ checkPositionsForExits(): 익절/손절/급등/장기 청산 ✅

자동매매 설정 (AutoTradingSettings)
  ├─ unitSize / lineUnits[N] (레인보우 라인별 유닛) ✅
  ├─ maxPositions / maxDailyTrades ✅
  ├─ takeProfitPercent / stopLoss / surgeThreshold / stalePeriodDays ✅
  ├─ minAiConfidence 슬라이더 ✅
  ├─ themeWeight / newsWeight / financialsWeight / liquidityWeight / institutionalWeight ✅
  ├─ requireGoodFinancials / requireHighLiquidity 스위치 ✅
  └─ requireMarketIssue 스위치 (코드 구현됨, UI도 있음) ✅

AI 분석 페이지
  ├─ /api/ai/analyze-stock → GPT analyzeStock() ✅
  ├─ /api/ai/analyze-portfolio ✅
  └─ /api/ai/integrated-analysis ✅

계좌 / 잔고
  ├─ 계좌 CRUD (dashboard) ✅
  ├─ 잔고 자동갱신 (5분 BalanceRefreshService, KST 08:30~18:00) ✅
  └─ 보유종목 실시간 표시 ✅

주문 / 거래내역
  ├─ 수동 매수/매도 주문 ✅

  ├─ 종목 추가/삭제 ✅

설정
  ├─ GPT 모델 선택 ✅
  └─ 트레이딩 모드 (실계좌/모의) ✅
```

### M-5. Pending 주문 자동 만료 — 매매잡 의존 문제

**현황:**  
`expireOldPendingOrders()`는 `processModel()` 내부에서만 호출됨.  
매매잡이 꺼져 있으면 오래된 pending이 영원히 대기 상태로 남음.

오늘 DB에서 수동 취소 처리 완료:
```sql
UPDATE orders SET order_status = 'cancelled'
WHERE order_status = 'pending' AND created_at < NOW() - INTERVAL '1 day';
-- 결과: 7행 취소
```

**구현해야 할 내용:**

```
서버 시작 시 자동 실행 또는 별도 타이머:
server/index.ts 또는 routes/index.ts에:

// 서버 시작 후 1회 실행 + 이후 1시간 주기
setTimeout(async () => {
  const accounts = await storage.getAllAccounts();
  for (const acc of accounts) {
    await orderSyncService.expireOldPendingOrders(acc.id);
  }
}, 5000);
setInterval(같은 로직, 3600000);  // 1시간마다
```

**우선순위:** 높음 (서비스 재시작 시마다 수동 처리 필요)

## 5-1. ⛔ 구현 시 안전 규칙 (기존 기능 파괴 방지)

아래 3가지를 반드시 지켜야 기존 매매 파이프라인·잔고 갱신이 깨지지 않음.

### 규칙 1: trade-executor 안의 notification / updateCandidateStock → fire-and-forget

`evaluateCandidateStock()`, `evaluateStock()`, `executeBuy()`, `executeSell()` 안에
`storage.createEngineNotification()` 또는 `storage.updateCandidateStock()`을 추가할 때,
**절대 bare `await`로 호출하면 안 됨.**

```typescript
// ❌ 위험: notification throw 시 return 누락 → 스킵해야 할 종목이 매수될 수 있음
if (marketAnalysis.confidence < minConf) {
  await storage.createEngineNotification({...});  // throw하면 return 안 됨!
  return;
}

// ✅ 안전: fire-and-forget (notification 실패해도 매매 흐름 무영향)
if (marketAnalysis.confidence < minConf) {
  storage.createEngineNotification({...}).catch(e => console.error('[Notification]', e));
  return;
}

// ✅ 안전: 개별 try/catch (notification 실패 격리)
if (marketAnalysis.confidence < minConf) {
  try { await storage.createEngineNotification({...}); } catch(e) { console.error(e); }
  return;
}
```

**이유**: `evaluateCandidateStock` (line 636)과 `evaluateStock` (line 66) 모두 최상위 try/catch가 있어서,
return 직전의 await가 throw하면 return이 실행되지 않고 catch로 빠짐.
→ confidence 미달 종목이 스킵되지 않거나, DART 위험공시 종목이 차단되지 않을 수 있음.

### 규칙 2: BalanceRefreshService 스냅샷 저장 → 별도 try/catch 격리

```typescript
// balance-refresh.service.ts refreshAccount() 마지막에 추가 시:

// ❌ 위험: 스냅샷 저장 실패 시 잔고 갱신 전체가 실패로 처리됨
await storage.createAssetSnapshot({...});

// ✅ 안전: 스냅샷 실패와 잔고 갱신을 격리
try {
  await storage.createAssetSnapshot({...});
} catch (e) {
  console.error('[BalanceRefresh] 스냅샷 저장 실패 (잔고 갱신은 정상):', e);
}
```

**이유**: `refreshAccount()`의 외부 try/catch에 잡히면,
이미 성공한 holdings 갱신까지 "실패"로 표시될 수 있음.

### 규칙 3: candidate_stocks 신규 컬럼 → 반드시 nullable

```typescript
// ✅ 안전: 3개 모두 nullable (기존 scanJob INSERT 보호)
evaluationResult: jsonb("evaluation_result"),           // nullable — OK
skipReason: text("skip_reason"),                        // nullable — OK
evaluatedAt: timestamp("evaluated_at"),                 // nullable — OK

// ❌ 위험: NOT NULL이면 scanJob의 기존 upsertCandidateStock()이 깨짐
evaluationResult: jsonb("evaluation_result").notNull(),  // scanJob에서 이 값 안 넣음 → INSERT 실패!
```

**이유**: scanJob은 `upsertCandidateStock({userId, modelId, stockCode, stockName, source, scannedLine})`만 호출.
새 컬럼이 NOT NULL이면 DB에서 INSERT 거부 → 후보 종목 수집 자체가 중단됨.
